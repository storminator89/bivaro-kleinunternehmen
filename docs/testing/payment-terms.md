# Payment-day defaults

## Scope

New ordinary invoices, including quote conversions, propose a due date using the
selected customer’s payment days, then the company setting, then the existing
14-day fallback. Defaults are optional integers from 0 through 365. Blank means
inherit; zero explicitly means the invoice date. Templates do not carry customer
payment terms or dates. Service-plan drafts retain their existing contract.

PDF date labels and XML use the same calendar day independently of the viewer’s
timezone. These are editable calendar-date suggestions, not discounts, interest,
collection rules, payment instructions or a legal-effect claim. No existing
invoice, journal entry or historical due date is migrated or recalculated.

## Editor contract

- The suggestion follows invoice-date changes until the due date is manually
  edited or explicitly retained. Manual dates survive later profile, date and
  customer changes.
- Customer changes ask before replacing a manually edited due date. Declining
  keeps that date while allowing the new customer selection.
- **Vorgabe erneut anwenden** reloads current company and customer data and
  deliberately replaces the due-date suggestion. Interrupted, superseded and
  failed requests do not overwrite newer manual edits.
- The short source hint distinguishes customer, company, fallback and manual
  decisions. No browser-persistent cache is added.

## Persistence and concurrency

The additive migration adds nullable `paymentTermDays` columns to `Customer`
and `Settings`, without defaults or backfills. The server rejects non-integer,
out-of-range and incorrectly typed values. Existing tenant ownership and
mutation protection remain in force.

Generated ordinary uploads may supply a bounded `paymentTermSelection` snapshot
in parsed document data: version 1, source, days, invoice date, actual due date
and customer relation. Dates are ISO calendar dates. A manual selection has null
days and may retain the existing optional due date. Submitted metadata must
match the parsed invoice and selected tenant customer. The commit transaction
checks current defaults; stale automatic choices return HTTP 409 instead of
rewriting generated bytes. A deliberate manual choice remains valid.

The generated-request fingerprint includes the canonical selection when one is
present. Replaying an already saved request returns its immutable result before
checking newer defaults. Reusing the request with different provenance conflicts.
Older uploads without metadata remain compatible and gain no invented default
history. Legacy JSON invoice/quote creation cannot claim reserved provenance.
New credit notes omit the original invoice’s selection while preserving that
original evidence unchanged. Service-draft metadata injection is rejected.

## Backup contract

The exact current capability identity is
`20261022040000_add_payment_terms`. The preceding
`20261022030000_combine_projects_outbox_validation` identity remains explicitly
supported, retaining projects, durable mail outbox and purchase validation, but
not gaining payment-term capabilities. No capability is inferred from timestamps.

- New exports include defaults and any frozen invoice selection.
- Older identities accept absent/null future fields but reject non-null defaults
  or selection snapshots rather than discard them.
- Restoration validates days, snapshot shape, source/version, invoice type,
  dates, customer relation and numbered ordinary-document identity.
- Customer IDs inside snapshots are remapped with their invoice relation.
  Number collisions with absent, conflicting or invalid provenance are rejected
  atomically. Reimport cannot silently replace source, days or dates.
- Merge skips preserve existing customer defaults; an existing target company
  default is retained. New records and replacement restores receive the source
  defaults. Mail-outbox histories and incoming-validation reports keep their
  existing restoration rules.

## Verification boundary

Focused domain, API and backup tests use synthetic fixtures and fresh temporary
SQLite databases. They cover null/zero, 14/30/365 days, strict validation, leap
and month/year boundaries, DST-independent calendar arithmetic, transactional
staleness, manual selection, tenant boundaries, immutable replay/history,
backup round trips, remapping, collisions and historical identities. Existing
invoice, service-draft, fiscal, quote, outbox and backup regression suites are
also exercised by the local candidate checks.

`e2e/payment-terms.spec.ts` is authored for the existing supported hosted
Chromium runner. It is **not executed** as part of this local handoff. Browser
acceptance, responsive visual inspection and the production build remain
unverified. No workflow change, CI run, publication or release is included.
